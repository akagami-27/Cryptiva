# Cryptiva STRIDE Threat Model and Risk Assessment

## Scope and evidence

This model describes the checked-out Cryptiva source and infrastructure configuration, not an independently inspected production environment. Evidence includes Express middleware and routes, Mongoose models, crypto/file services, tests, Docker/Compose files, `.dockerignore`, the GitHub Actions workflow, and Kubernetes manifests. No secrets, `.env` values, user files, database contents, or storage contents were inspected.

The reviewed `server.js` imports `registerReactPages` and registers the React page routes. The workflow runs automated tests and a frontend build but does not run a pre-publication server-start smoke test. The source-level route registration is present; full backend startup, external-service connections, and production behavior remain unverified. This is a verification gap, not evidence of a current startup failure or production incident.

Controls below are classified as:

- **Implemented:** present in the inspected source/configuration.
- **Partially implemented:** a control exists but does not cover the entire risk or has an operational dependency.
- **Unverified:** repository evidence cannot establish live infrastructure or operation.
- **Proposed:** recommendation only; not implemented.

## System and trust boundaries

See [system architecture](../architecture/system-architecture.mmd) and [deployment architecture](../architecture/deployment-architecture.mmd). The main boundaries are the user browser to Express, the Kubernetes workload to configured MongoDB and Supabase endpoints, and the GitHub Actions workflow to Harbor/Kubernetes credentials. The manifests declare an Ingress TLS configuration and external service settings; their live existence and enforcement were not verified.

File contents are plaintext in the browser and in the server's temporary upload staging area before encryption. The backend computes SHA-256, encrypts file bytes using a random per-file DEK with AES-256-GCM, wraps the DEK with the configured master key, and sends ciphertext to Supabase Storage. MongoDB stores account and file metadata, encryption parameters, wrapped keys, SHA-256 values, sessions, share state, rate-limit buckets, and audit records. Downloads retrieve ciphertext, unwrap the DEK, decrypt, verify the stored SHA-256, then return plaintext to an authorized browser.

## Risk method

Likelihood (L) and impact (I) use qualitative 1–5 scales. Each score is an engineering judgment based on the scenario, exposure, attacker capability, existing controls, and plausible effect. Scores are not measured probabilities or calibrated loss estimates.

| Score | Likelihood interpretation | Impact interpretation |
|---|---|---|
| 1 | Rare under expected operation | Negligible, easily recoverable |
| 2 | Unlikely but plausible | Minor, limited users or short disruption |
| 3 | Plausible | Moderate confidentiality, integrity, or availability effect |
| 4 | Likely under the scenario | Major effect across users or sensitive files |
| 5 | Expected or readily repeatable | Severe or broad compromise/outage |

Risk score = L × I. Bands: 1–4 Low, 5–9 Moderate, 10–16 High, 17–25 Critical. Scores prioritize investigation; they do not mean the threat has occurred.

## Rationale for qualitative scores

Likelihood and impact are judged separately for each scenario. Likelihood reflects exposure and the effort or access needed to exploit it after accounting for the controls listed in the threat register. Impact reflects the plausible confidentiality, integrity, or availability effect if that scenario succeeds. These are qualitative judgments, not measured probabilities or empirical loss estimates.

| ID | Likelihood rationale | Impact rationale |
|---|---|---|
| S-01 | **3 — Plausible:** authenticated endpoints are Internet-facing, but token theft generally requires browser, device, or credential compromise; expiry and token-version checks limit replay. | **4 — Major:** a valid account token can expose that account's files and permit account-level file or share actions. |
| S-02 | **2 — Unlikely:** guessing a 256-bit random token is impractical, and password attempts are rate-limited; forwarding or leakage of a valid bearer link remains possible. | **4 — Major:** successful access can disclose the specific shared file and its contents. |
| T-01 | **2 — Unlikely:** storage alteration or corruption can occur, but AES-GCM authentication and SHA-256 checks detect the described changes before release. | **4 — Major:** undetected corruption could compromise file integrity; detected corruption blocks access to the affected file. |
| T-02 | **2 — Unlikely:** session-bound CSRF validation and SameSite cookies constrain cross-site requests; an attacker needs a victim browser and a route not protected by these controls. | **4 — Major:** a successful state-changing request could modify or delete account-owned files or shares. |
| T-03 | **2 — Unlikely:** concurrent requests can race, but atomic reservations, leases, and idempotent settlement are designed to prevent limit overruns. | **3 — Moderate:** a failure could exceed the configured count for one share and undermine its access limit. |
| R-01 | **3 — Plausible:** disputes can arise during normal operation, and privileged database access or best-effort audit failures are credible scenarios. | **3 — Moderate:** missing or altered records weaken investigation and accountability but do not by themselves disclose or alter file contents. |
| I-01 | **3 — Plausible:** the database is an external dependency and credentials or access policies can be compromised, while separate key wrapping limits a database-only compromise. | **4 — Major:** database access exposes account, filename, sharing, audit, and wrapped-key metadata; combined compromise of the master key could expose file keys. |
| I-02 | **3 — Plausible:** uploads necessarily pass through plaintext staging and memory; cleanup and ephemeral storage reduce, but cannot eliminate, host or crash-artifact exposure. | **4 — Major:** successful host-level access could disclose the affected staged file or plaintext buffer. |
| I-03 | **2 — Unlikely:** access requires service-role credential or bucket-policy compromise; encryption limits direct disclosure of stored ciphertext. | **3 — Moderate:** storage access can expose ciphertext and object-level information; plaintext disclosure requires additional key compromise. |
| D-01 | **3 — Plausible:** upload endpoints accept large files and concurrent work, although per-file limits, scanner bounds, and a volume limit constrain consumption. | **4 — Major:** saturation could exhaust temporary storage or scanner capacity and make upload or broader application service unavailable. |
| D-02 | **3 — Plausible:** MongoDB, Supabase, DNS, and ClamAV are external or separately operated dependencies that can experience outages despite normal controls. | **4 — Major:** dependency failure can interrupt startup, authentication, or file operations for users. |
| D-03 | **2 — Unlikely:** the current route import/registration is present; the likelihood is for a future regression escaping tests because CI lacks a pre-publication startup check. | **4 — Major:** if such a regression prevents the listener from starting, the application can be unavailable until detected and corrected. |
| E-01 | **2 — Unlikely:** authenticated users can manipulate object IDs, but protected routes use owner-constrained lookups; exploitation would generally require a missing or regressed check. | **5 — Severe:** a successful authorization bypass could expose or change other users' files across accounts. |
| E-02 | **3 — Plausible:** the pipeline consumes third-party actions and privileged deployment credentials; validation and limited workflow permissions reduce but do not remove supply-chain risk. | **5 — Severe:** a successful compromise could publish a malicious image or alter the production deployment. |
| E-03 | **2 — Unlikely:** container or cluster privilege escalation requires a successful exploit; seccomp, disabled privilege escalation, and no service-account token reduce opportunities. | **5 — Severe:** successful cluster pivoting could expose application secrets or affect other workloads, depending on cluster isolation. |

## Highest-priority residual risks

1. **Startup verification gap:** CI has no pre-publication server-start smoke test. Add an isolated check to detect a future startup regression before image publication; no current failure or production incident is established.
2. **High availability/resource risk:** concurrent uploads can consume substantial staging capacity while scanner concurrency is bounded. Add aggregate upload quotas and exercise saturation.
3. **High data/key risk:** MongoDB and Supabase policies, backup access, transport security, and master-key rotation are external operational controls and were not verified.
4. **High pipeline/runtime risk:** CI has no dependency/SAST/container scan, actions are not pinned by immutable SHA, and pod hardening is incomplete in the manifests.
5. **Audit assurance:** MongoDB audit logs are not demonstrated as immutable, and successful actions can continue if some audit writes fail.

## Evidence limits

- The local `npm test` run completed **203 passed, 6 skipped, 0 failed**. The skipped cases are MongoDB integration tests requiring a dedicated test URI. The tests do not start the production server or contact production MongoDB/Supabase.
- The workflow configuration in the repository includes test/build, image publication, rollout, and health checks. The project owner reported a successful GitHub Actions run, but its run ID and logs were not independently inspected. This report does not infer a deployed revision or verified production behavior from that report.
- No browser upload, live malware scan against production services, cloud policy review, image scan, Kubernetes cluster inspection, backup/restore test, or production penetration test was performed.
- Scores are qualitative and should be reviewed with project supervisors and operational owners.
