# Isolated integration testing

## MongoDB reservation integration tests

The six tests in `tests/shareDownloadReservations.mongo.test.js` exercise concurrent admission at a one-download limit, expired-reservation pruning, successful settlement, idempotent settlement, share/reservation isolation, and concurrent settlement. They use the production `ShareLink` schema bound to test-only collections.

Each test generates a distinct database name (`crt_*`, `cre_*`, or `crs_*`) and calls `dropDatabase()` for that database in test cleanup. The test collections are `share_link_reservation_tests`, `share_link_expiry_tests`, or `share_link_settlement_tests`. The configured URI must name a database containing a `test` segment; Mongoose then uses the generated database name for that test. The test URI must not use the same MongoDB host as the application's `MONGODB_URI` (the guard also checks the root `.env` without printing its values). A remote target additionally requires an explicit disposable-cluster acknowledgement.

**Use a separate local disposable MongoDB instance when practical, or a new disposable non-production test cluster with a separate test-only account.** Do not use the production cluster, the application's database, or the application's credentials. Because tests generate database names and drop each one, the test account needs permissions to create databases and collections, create indexes, read/write test documents, and drop the generated databases. These permissions are destructive across the account's permitted scope, which is why the test cluster must contain no other data. Do not grant this test account production access.

The current checkout has no `mongod`, `mongosh`, Docker, or Podman executable detected, and no `MONGODB_TEST_URI` is configured. No database connection or cleanup was performed. Install/start an isolated local test instance or provision a disposable test-only cluster yourself before running the integration tests.

Set the URI in the current PowerShell process without putting it in chat or a committed file. For a remote disposable cluster, set the explicit acknowledgement only after confirming the cluster is test-only:

```powershell
$secureUri = Read-Host 'Dedicated MongoDB test URI' -AsSecureString
$uriPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secureUri)
try {
    $env:MONGODB_TEST_URI = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($uriPointer)
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($uriPointer)
}
# Remote disposable cluster only, after verifying isolation:
$env:MONGODB_TEST_ALLOW_REMOTE = 'I_UNDERSTAND_THIS_IS_DISPOSABLE'
npm test -- --test-name-pattern='MongoDB'
Remove-Item Env:MONGODB_TEST_URI -ErrorAction SilentlyContinue
Remove-Item Env:MONGODB_TEST_ALLOW_REMOTE -ErrorAction SilentlyContinue
```

For local MongoDB, omit `MONGODB_TEST_ALLOW_REMOTE`. The normal full suite skips these six tests when `MONGODB_TEST_URI` is absent. It never falls back to `MONGODB_URI`.

## Supabase Storage integration checks

There is no live Supabase integration test in the existing suite. Current route tests mock Supabase; they do not verify real bucket policy, ciphertext at rest, network failures, or cleanup against a project. The application uses `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_BUCKET`; the bucket defaults to `cryptiva-files` and must be private. Upload creates an `uploading` Mongo record, encrypts bytes before upload, then marks the record active. Download fetches ciphertext, decrypts it, and checks SHA-256 before returning plaintext. Delete marks metadata as deleting before removing the object and records a retryable failure if cleanup fails.

For a future live test, configure a separate non-production Supabase project and a dedicated private test bucket using test-only credentials. Keep the test project free of user files. Use a new test account and harmless generated bytes, and capture only object path, response status, and non-secret assertions. For each created object, verify through the Supabase SDK or project dashboard that downloaded raw object bytes differ from the test plaintext; verify unauthenticated access is denied; then exercise authorized application download and compare the result with the original test bytes. A dedicated test harness can tamper only with that newly created object, verify the application rejects it, and then remove only that exact object path in `finally` cleanup. Also induce upload/download/remove failures in the test harness or a controlled test bucket and inspect that metadata is active, retryable, or removed according to the observed operation. Never enumerate and clear a shared bucket, use real files, or print keys, passwords, cookies, JWTs, or storage credentials.

No Supabase test project or dedicated bucket was identified in this checkout. No live storage operation, test object creation, modification, or deletion was performed. Do not point the current `.env` Supabase configuration at a test run unless its project and bucket have first been verified as non-production and disposable.
